# Cluster Requirements

This document defines the minimum cluster specification required to run the
storage certification harness. These requirements apply to all partner-level
certification runs.

---

## Topology

| Requirement                 | Value                                                             |
| --------------------------- | ----------------------------------------------------------------- |
| Cluster type                | Multi-node OpenShift (see below)                                  |
| Control-plane nodes         | 3 (HA etcd quorum required)                                       |
| Worker nodes                | **≥ 3** (storage workloads must be schedulable on multiple nodes) |
| Single-Node OpenShift (SNO) | **Not supported** — excluded by design                            |

SNO clusters cannot satisfy the multi-node scheduling and HA requirements of
storage certification workloads.

---

## OpenShift Version

| Requirement         | Value                                                  |
| ------------------- | ------------------------------------------------------ |
| Minimum OCP version | **4.20**                                               |
| Recommended         | Latest GA release in the 4.x stream                    |
| EUS / LTS streams   | Supported when the version satisfies the minimum above |

The harness interacts with the cluster via the Kubernetes API
(`client-go`/`controller-runtime`); it does not use features that are
OCP-version-gated beyond the 4.20 baseline.

## Hardware Minimums

### Control-plane nodes (×3)

| Resource  | Minimum                                                         |
| --------- | --------------------------------------------------------------- |
| vCPU      | 8                                                               |
| RAM       | 32 GB                                                           |
| Root disk | 120 GB — **NVMe SSD required; SAS SSD is the absolute minimum** |
| Network   | 10 Gbps                                                         |

> etcd is co-located on control-plane nodes and is extremely sensitive to disk
> latency. Slow disks (SATA SSD or spinning HDD) cause etcd heartbeat timeouts,
> leader elections, and cascading API-server instability under the I/O load
> generated by certification workloads. Use NVMe where possible; SAS SSD is the
> hard floor. SATA SSD and HDD are **not supported**.

### Worker nodes (×3 or more)

| Resource  | Minimum                 |
| --------- | ----------------------- |
| vCPU      | 16                      |
| RAM       | 64 GB                   |
| Root disk | 120 GB (OS + ephemeral) |
| Network   | 10 Gbps                 |

> For performance-tier certification (e.g. latency / IOPS tests) 16 vCPU /
> 64 GB RAM per worker is recommended to avoid CPU/RAM saturation masking
> storage bottlenecks.

### Storage Connectivity

#### iSCSI and FC — multipath

`multipathd` must be enabled and the CSI driver's multipath configuration
applied on **all worker nodes before the CSI driver is installed** — the driver
reads the multipath config at startup. Required for both iSCSI and FC.

#### iSCSI

| Requirement    | Minimum                                      | Recommended (failover testing)            |
| -------------- | -------------------------------------------- | ----------------------------------------- |
| Ethernet links | 1 dedicated NIC port (functional tests only) | 2 dedicated NIC ports on separate uplinks |

The right network topology depends on how your storage array's iSCSI portals
are addressed and on the vendor's CSI driver implementation — some drivers
manage iface binding or multipath session setup automatically, while others
expect the host network to be pre-configured. Consult your CSI driver's
documentation before deciding on a topology.

##### Portal IPs on different subnets (preferred)

Give each physical NIC its own IP address on a separate subnet — one subnet per
storage portal. The iSCSI initiator establishes independent TCP connections to
each portal simultaneously, giving true multipath at the initiator level.
Configure the per-NIC IP addresses on the worker nodes via a
`NodeNetworkConfigurationPolicy` (NNCP).

##### Portal IPs on the same subnet

Two NICs on the same subnet can still achieve true iSCSI multipathing without
bonding by using **iSCSI interface binding (ifaces)** — each initiator interface
is bound to a specific NIC by MAC address, so the iSCSI stack sends traffic
over both physical links independently even though they share a subnet. This is
the preferred approach when both portals are on the same network.

If you choose to bond the NICs instead, use **Active-Backup** bond mode
(`mode=1`), not LACP (802.3ad). LACP hashes traffic by MAC/IP combination;
because all iSCSI sessions target the same storage cluster, it will typically
hash everything to a single physical cable, defeating the purpose. Active-Backup
guarantees an immediate failover to the standby NIC if the active link fails,
at the cost of not using both links simultaneously.

#### Fibre Channel (FC)

| Requirement     | Minimum                                                                                           | Recommended (failover testing)                                                              |
| --------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| HBAs per worker | 1 dual-port HBA                                                                                   | 2 single-port HBAs (independent PCIe slots)                                                 |
| FC switches     | 1 switch connecting all worker ports to the array                                                 | 2 switches — one per HBA/port group, each connected to a separate set of array target ports |
| Zoning          | WWPNs of each worker zoned to target array ports; single-initiator-single-target zoning preferred | Same, replicated per fabric                                                                 |

> A single dual-port HBA provides two paths through a single card — adequate
> for redundant-path I/O but not a true hardware-failure simulation. Two
> independent HBAs across two independent fabrics (switches) are needed to
> exercise real FC failover scenarios.

#### NVMe-oF

NVMe-oF supports multiple transports; the hardware required on each worker node
depends on which transport the array uses:

| Transport                      | Worker hardware required                                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| NVMe-oF/TCP                    | Standard Ethernet NIC (same NIC used for general cluster traffic is acceptable)                                                             |
| NVMe-oF/RDMA (RoCE v2 / iWARP) | RDMA-capable NIC; switch must support lossless Ethernet (PFC / ECN) for RoCE v2                                                             |
| NVMe-oF/FC                     | FC HBA with **NVMe/FC** support — standard SCSI/FC HBAs are not sufficient; confirm NVMe/FC firmware and driver support with the HBA vendor |

> **Known issue — duplicate `hostnqn` across OCP nodes:** OCP node
> provisioning can generate identical `hostnqn` values, preventing the array
> from distinguishing initiators
> ([Red Hat solution 7073579](https://access.redhat.com/solutions/7073579)).
> Verify and correct `hostnqn` uniqueness on all worker nodes **before**
> installing the NVMe-oF CSI driver.

## Storage Prerequisites

Two categories of storage are required:

### 1. Cluster ephemeral storage

Standard OCP ephemeral storage backed by the root disk of each node. No
additional provisioning needed beyond the root-disk minimums above. The
control-plane root disk doubles as the etcd data volume, so the NVMe / SAS SSD
requirement above applies here as well.

### 2. Storage under test

| Requirement         | Details                                                                       |
| ------------------- | ----------------------------------------------------------------------------- |
| StorageClass        | The `StorageClass` under certification must exist in the cluster              |
| VolumeSnapshotClass | Required — must be created and backed by the CSI driver under test            |
| Provisioner health  | All `CSIDriver` pods must be running and Ready before preflight               |
| Capacity            | Sufficient for the test plan's PVC requests (see the plan's `backend:` block) |

Provide the storage array details in a `backends.yaml` file (see
`backends.example.yaml`). The backend name referenced by the test plan must
match an entry in that file.

#### CDI scratch space

Test plans that exercise VM image import or data-volume workflows use the
**Containerized Data Importer (CDI)**. CDI requires a scratch `PersistentVolume`
during import operations, and that scratch PVC **must be backed by a
file-based (filesystem-mode) `StorageClass**` — block-mode StorageClasses are
not usable as CDI scratch space.

| Requirement                | Details                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------ |
| CDI scratch `StorageClass` | A `filesystem`-mode `StorageClass` must exist in the cluster                         |
| Configuration              | Set via `CDIConfig.spec.scratchSpaceStorageClass`                                    |
| Capacity                   | Must accommodate the largest image under test — scratch PVCs match source image size |

## HA Testing — Node Remediation

For test plans that exercise high-availability and failover scenarios, OCP node remediation must be configured so the cluster can automatically detect and recover unhealthy nodes.

The recommended stack is the **Node Health Check (NHC) operator** paired with
a remediation provider:

| Component                                                                                                                                  | Purpose                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| [Node Health Check Operator](https://github.com/medik8s/node-healthcheck-operator)                                                         | Detects unhealthy nodes based on configurable conditions                  |
| [Self Node Remediation (SNR)](https://github.com/medik8s/self-node-remediation)                                                            | Node reboots itself when fenced — no external fencing hardware required   |
| [Fence Agents Remediation (FAR)](https://github.com/medik8s/fence-agents-remediation)                                                      | Hardware/platform fencing via fence agents (IPMI, AWS, vSphere, etc.)     |
| [Machine Health Check (MHC)](https://docs.openshift.com/container-platform/latest/machine_management/deploying-machine-health-checks.html) | OCP-native alternative; remediates via the Machine API (IPI/UPI clusters) |

Choose the remediation provider that matches your infrastructure.

## What Is Explicitly Out of Scope

- Disconnected / air-gapped clusters — supported in principle via image mirroring
  but not covered by this document.
- Hosted-control-plane (HCP/Hypershift) clusters — not validated yet.
- FIPS mode — not tested; known incompatibilities may exist.
